EHDS Connect — KI-gestützte IPS & Entlassungsbrief

Team Briefing · Branch: patientSummary · Repo: github.com/monael6/ehds-connect

⚠ Hackathon-Demonstrator · Kein Produktionseinsatz

Was wurde gebaut

Ein End-to-End-System das alle Krankenhausdokumente eines Patienten liest und daraus automatisch erzeugt:

OutputFormatStatus
International Patient Summary (IPS)HL7 FHIR R4 Bundle, IPS IG 2.0.0Immer preliminary bis Arzt freigibt
Entlassungsbrief-EntwurfMarkdown, Deutsch, mit QuellenreferenzenJeder Satz zitiert Dokument-IDs
EvaluierungsberichtJSON (Precision/Recall)Nur im synthetic-Modus

Architektur

Pipeline (CLI · run.py)

1Datenschutz-Gate
Prüft Modus + DSGVO-Checkliste. Bricht ab wenn Voraussetzungen fehlen.
2Pseudonymisierung
Ersetzt Namen/DOB/SVNr/Einrichtung durch Tokens. Mapping nur im RAM.
3LLM-Extraktion
Sendet nur pseudonymisierten Text. Striktes JSON-Schema, Retry-Logik.
4Zitat-Verifikation
Deterministischer Substring-Check jedes Zitats gegen Quelldokument.
5Terminologie-Validierung
ICD-10 / ATC / SNOMED lokale Lookup-Tabellen. Unbekannte Codes → text-only.
6FHIR-Mapping
Deterministisch. Kein LLM-FHIR-Schreiben. Re-Identifikation hier.
7FHIR-Validierung
HL7 validator_cli.jar gegen IPS IG 2.0.0 + optional AT-APS IG.
8Evaluierung
Nur synthetic: Vergleich mit ground_truth_ips.json. Ground Truth nie ans LLM.
9Entlassungsbrief
Deutsch, österreichischer Stil, jeder Satz mit [P00X-D00Y] Quellen.

Datenschutz & Sicherheit

Implementierte Maßnahmen

Pseudonymisierung vor jedem LLM-Aufruf — Namen, Geburtsdatum, Versicherungsnummer, Einrichtungsname werden durch Tokens ersetzt. Mapping-Tabelle lebt nur im RAM.
LLM schreibt nie FHIR — Das LLM gibt nur ein intermediäres JSON-Schema zurück. FHIR-Mapping ist deterministischer Code.
Practitioner-ID nur aus OIDC-Token — Nie aus Request Body. AuthenticatedPractitioner ist nach Konstruktion unveränderlich (__slots__ + __setattr__).
Composition immer preliminary — Wird erst auf final gesetzt wenn Arzt aktiv Checkbox ankreuzt und keine roten Items oder Validator-Fehler bestehen.
KI ist assembler, nicht author — In FHIR Provenance und Composition. Author wird erst bei Freigabe durch den Arzt gesetzt.
AuditEvent für jede Lese-/Schreiboperation — Kein klinischer Inhalt in Audit-Logs. Nur Timestamp, Pseudonym-Token, Modus, Modellname, Erfolgsstatus.
AES-256-GCM Verschlüsselung — Alle Outputs im pseudonymized/real Modus werden verschlüsselt geschrieben.
DSGVO-Gate — Modi pseudonymized/real erfordern deployment.yaml mit vollständiger DSGVO-Checkliste (Art. 9, Art. 28, Art. 35 DPIA). Fehlendes oder unvollständiges File → Abbruch.
Keine Secrets im Repo — .env, deployment.yaml, output/, frontend/.env.local in .gitignore.
KI-Disclaimer in jedem Output — Jede Composition und jeder Entlassungsbrief enthält: "KI-generierter Entwurf, ärztliche Prüfung erforderlich".
Für echten klinischen Einsatz zusätzlich erforderlich: DPIA nach Art. 35 DSGVO · AVV mit LLM-Anbieter (Art. 28) · MFA für klinisches Personal · TLS 1.3 überall · Penetrationstest · ISO 27001 / IEC 27799 · MDR/EU AI Act Konformitätsbewertung

Quick Start

Option A — Nur Tests (kein LLM, kein Docker)

pip install -r requirements.txt
pytest tests/ -v
# → 47/47 passed

Option B — CLI Pipeline (braucht LLM-Key)

# 1. .env anlegen
cp .env.example .env
# LLM_PROVIDER=openai + OPENAI_API_KEY=sk-... eintragen

# 2. Pipeline starten (synthetic = kein DSGVO-Aufwand)
python run.py --patient P001 --mode synthetic

# Outputs in output/P001/
#   ips_bundle.json          ← FHIR R4 Bundle
#   discharge_summary_draft.md
#   evaluation_report.json   ← Precision/Recall vs Ground Truth
#   audit_log.jsonl

Option C — Vollständiger Docker-Stack

# Aus dem Repo-Root:
docker compose up -d
# ~2 Min warten bis HAPI FHIR + Keycloak hochgefahren sind
docker compose ps

# Frontend:
http://localhost:5173

Option D — Nur Frontend entwickeln (kein Docker)

# frontend/.env.local enthält bereits VITE_DEV_SKIP_AUTH=false
# Zum lokalen Testen ohne Docker auf true setzen:
# VITE_DEV_SKIP_AUTH=true in frontend/.env.local
cd frontend
npm install && npm run dev
